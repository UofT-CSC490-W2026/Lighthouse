\section{Context for Our Project: Lighthouse}

Lighthouse is a code search engine exposed via the Model Context Protocol (MCP) that
improves the performance of AI coding agents by surfacing relevant context from a
codebase. A developer selects GitHub repositories to index, Lighthouse ingests and
indexes them, and the developer adds the Lighthouse MCP server to their AI coding
agent. When the agent is working on a task and needs context that falls outside its
immediate working scope, it queries Lighthouse to retrieve relevant code snippets,
interfaces, and documentation.\\

The system is composed of several services: an \textbf{ingestion service} that clones
repositories, chunks source files, generates embeddings, and stores them in Postgres
and Milvus (vector database) via Temporal (distributed, durable execution solution) workflows; a \textbf{search service} that implements retrieval
strategies (e.g.\ hybrid search combining dense vector similarity with sparse keyword
matching); an \textbf{MCP server} that exposes search as MCP tools consumable by coding
agents; and a \textbf{web service} for management and visualization (currently used for debugging).

\subsection{Current State}

We have implemented a baseline version of the full pipeline: repositories can be indexed
(with both full and incremental indexing), searched via the MCP server, and results are
returned to coding agents. However, several areas are still in active development:

\begin{itemize}
  \item \textbf{Web UI} --- The web service currently serves as a debugging interface
    for internal development. We are still discussing and formulating what the
    production UI will look like, and expect to redesign it in the coming week.
  \item \textbf{Evaluation suite} --- We are developing an eval suite to measure how
    effectively Lighthouse improves coding agent outcomes, building on the aspirational
    dataset design from A2. This will let us quantitatively compare retrieval strategies.
  \item \textbf{Search and ingestion experimentation} --- We are experimenting with
    different search strategies, chunking approaches (e.g.\ sliding window vs.\
    AST-aware chunking), and embedding models to improve retrieval quality beyond
    our current baseline.
\end{itemize}

\subsection{Tech \& Testing Stack}

\begin{itemize}
  \item \texttt{ingestion} --- A Python 3.11 service built with FastAPI and Temporal.
    It uses GitPython for repository cloning, our shared workspace packages
    (\texttt{shared}, \texttt{db}, \texttt{vectordb}, and \texttt{embedding}) for
    schemas and storage, and implements the indexing pipeline including chunking,
    embedding generation, and workflow orchestration.
  \item \texttt{search} --- A Python 3.11 FastAPI service that implements retrieval
    logic. It uses the same shared workspace packages as the ingestion service and
    contains our search strategies, including hybrid search over Postgres and Milvus.
  \item \texttt{mcp\_server} --- A Python 3.11 service built with FastAPI and
    FastMCP. It exposes Lighthouse functionality as MCP and HTTP endpoints for coding
    agents, and also uses \texttt{httpx}, \texttt{cryptography}, \texttt{asyncpg},
    and \texttt{boto3} for integration with authentication, persistence, and external
    services.
  \item \texttt{web} --- A TypeScript frontend built with React 19 and Vite. It uses
    React Router for navigation, SWR for client-side data fetching, and Tailwind CSS
    for styling; at the moment it primarily serves as an internal debugging and
    management UI.
\end{itemize}

For testing, our backend stack is centered on \texttt{pytest}, with tests organized
into \texttt{unit}, \texttt{integration}, and \texttt{e2e} markers. We use
\texttt{pytest-asyncio} for async service and API tests, and \texttt{pytest-cov} to
measure line coverage across the Python services and shared packages. For
infrastructure-dependent tests, we use \texttt{testcontainers} to provision isolated
Postgres and Milvus instances during test runs instead of depending on shared
developer machines. Since Temporal is a core part of the ingestion pipeline, we also
use Temporal Python SDK testing utilities such as
\texttt{temporalio.testing.WorkflowEnvironment} and
\texttt{ActivityEnvironment} to test workflow orchestration and activities in a
deterministic local environment.

\section{Showing Code Coverage}
% Using pytest-cov (https://github.com/pytest-dev/pytest-cov) or a similar library, show the code
% coverage of your project. Create a github workflow to generate your test coverage automatically on your
% readme and PRs. You can reference the example in pytest-cov or other open source projects

We use \texttt{pytest-cov} to measure line coverage across all Python source packages.
Coverage is automated via a GitHub Actions workflow at
\bluehref{https://github.com/UofT-CSC490-W2026/Lighthouse/blob/a5/.github/workflows/tests.yml}{.github/workflows/tests.yml},
which runs on every push to \texttt{main} and on every pull request.

The workflow performs the following steps:
\begin{enumerate}
  \item Runs \texttt{uv run pytest --cov --cov-report=xml --cov-report=term-missing} to
    execute all 293 tests and produce a coverage report.
  \item Parses the generated \texttt{coverage.xml} to extract the overall line coverage
    percentage and generate a colored badge.
  \item \textbf{On pushes to main:} updates the
    \bluehref{https://github.com/UofT-CSC490-W2026/Lighthouse/blob/main/README.md}{README.md}
    coverage badge in-place (between \texttt{coverage:start} / \texttt{coverage:end} markers)
    and commits the change automatically.
  \item \textbf{On pull requests:} posts (or updates) a comment on the PR with the current
    coverage percentage, so reviewers can see coverage impact at a glance.
\end{enumerate}

Our test suite consists of 293 tests (unit, integration, and end-to-end) achieving

\subsection{What We Measure}

Coverage is configured in
\bluehref{https://github.com/UofT-CSC490-W2026/Lighthouse/blob/a5/pyproject.toml}{pyproject.toml}
under \texttt{[tool.coverage.run].source} and includes all Python backend code:

\begin{itemize}
  \item \texttt{packages/db/src} --- Peewee ORM models and database utilities
  \item \texttt{packages/vectordb/src} --- Milvus vector database client wrapper
  \item \texttt{packages/embedding/src} --- Embedding provider abstraction (OpenAI, mock)
  \item \texttt{packages/shared/src} --- Shared data models and utilities
  \item \texttt{services/ingestion/src} --- Temporal workflows, activities, and chunking pipelines
  \item \texttt{services/search/src} --- Search strategies (hybrid search)
  \item \texttt{services/mcp\_server/src} --- MCP server, HTTP/MCP routers, auth, and decorators
\end{itemize}

\subsection{What We Exclude and Why}

\textbf{\texttt{services/web/}} is excluded from coverage measurement. This service is a
TypeScript/React frontend that currently serves as a debugging UI for internal development.
It is not part of our Python test suite and is being actively redesigned in the coming week,
so investing in test coverage for code that will be replaced would not be productive.
Once the new frontend stabilizes, we plan to add Playwright or similar end-to-end tests
for it separately.\\

We also use standard \texttt{exclude\_lines} patterns in our coverage configuration to
skip lines that are not meaningfully testable: \texttt{TYPE\_CHECKING} blocks,
\texttt{raise NotImplementedError} stubs, ellipsis-only bodies, and
\texttt{if \_\_name\_\_ == "\_\_main\_\_"} guards.

\section{Test Coverage Depth}
% Choose your most complex module in your codebase. Create at least 10 unit tests for this module that
% test edge cases, failure modes and important use cases. Link the tests and edge cases, and explain why
% you chose these tests in comments of that module. We’ll try to find addtional edge cases that exist to
% cause an error! Make sure to write positive tests and negative tests (ones that throw errors or gracefully

Our most complex module is the \texttt{IndexBranchWorkflow} in the ingestion service

(\bluehref{https://github.com/UofT-CSC490-W2026/Lighthouse/blob/a5/services/ingestion/src/ingestion/temporal/workflows/index\_branch.py}{services/ingestion/src/ingestion/temporal/workflows/index\_branch.py}).
This Temporal workflow orchestrates 7 distinct activities through a multi-step pipeline:
marking a branch as indexing, cloning the repository, chunking files into a staging table,
deleting old chunks, embedding chunks in parallel batches, storing results to the final
tables and vector database, and updating the branch status. It includes conditional
early-exit logic (when no chunks are produced), parallel fan-out for embedding batches
(using \texttt{asyncio.gather}), and a two-phase error handler that marks the branch as
failed and conditionally cleans up staging data only when a \texttt{batch\_id} has been assigned. \\

All 12 tests are located in
\bluehref{https://github.com/UofT-CSC490-W2026/Lighthouse/blob/a5/services/ingestion/tests/unit/test\_index\_branch\_workflow.py}{services/ingestion/tests/unit/test\_index\_branch\_workflow.py} and use Temporal's
\texttt{WorkflowEnvironment} with mocked activities. This isolates the workflow's
orchestration logic from external dependencies (Postgres, Milvus, git, OpenAI), allowing
us to test decision-making, parameter threading, and failure handling in under one second.

\subsection{Boundary Tests (Positive)}

These tests target the embed batching loop, which uses
\texttt{range(0, chunk\_count, EMBED\_BATCH\_SIZE)} where \texttt{EMBED\_BATCH\_SIZE = 512}.
Off-by-one errors in this loop would cause chunks to be silently skipped or duplicated.

\begin{enumerate}
  \item \textbf{test\_single\_chunk\_produces\_one\_embed\_batch} ---
    \texttt{chunk\_count=1} produces exactly 1 embed call at offset 0.
    Tests the lower boundary of the batching loop.

  \item \textbf{test\_exactly\_512\_chunks\_one\_batch} ---
    \texttt{chunk\_count=512} (exactly \texttt{EMBED\_BATCH\_SIZE}) produces exactly 1 batch.
    This is the upper boundary for a single batch; a fencepost error would produce 0 or 2 batches.

  \item \textbf{test\_513\_chunks\_two\_batches} ---
    \texttt{chunk\_count=513} is the smallest value that requires 2 batches.
    Verifies offsets are \texttt{[0, 512]}.

  \item \textbf{test\_large\_chunk\_count\_batch\_offsets} ---
    \texttt{chunk\_count=2049} produces 5 batches with offsets
    \texttt{[0, 512, 1024, 1536, 2048]}.
    Validates batch arithmetic at scale.
\end{enumerate}

\subsection{Failure Mode Tests (Negative)}

These tests verify that the workflow correctly handles exceptions at different stages.
The key invariant: \texttt{cleanup\_staging} is called if and only if \texttt{batch\_id}
was set (i.e., \texttt{chunk\_files} succeeded).

\begin{enumerate}[resume]
  \item \textbf{test\_delete\_failure\_triggers\_cleanup} ---
    \texttt{delete\_existing\_chunks} fails \emph{after} \texttt{batch\_id} is assigned.
    Verifies both \texttt{status="failed"} and \texttt{cleanup\_staging} are called.
    This failure point was not covered by existing e2e tests.

  \item \textbf{test\_store\_failure\_triggers\_cleanup} ---
    \texttt{store\_chunks} fails after embedding succeeds.
    Embedded staging rows must be cleaned up to avoid dangling data.

  \item \textbf{test\_chunk\_files\_failure\_no\_cleanup} ---
    \texttt{chunk\_files} raises \emph{before} \texttt{batch\_id} is assigned.
    Verifies \texttt{cleanup\_staging} is \textbf{not} called (there is nothing to clean),
    validating the \texttt{if batch\_id is not None} guard in the exception handler.
\end{enumerate}

\subsection{Parameter Propagation Tests (Positive)}

These tests verify that input parameters are correctly threaded through to the right activities.
Silent parameter drops would cause production failures with no error signal.

\begin{enumerate}[resume]
  \item \textbf{test\_github\_token\_propagated} ---
    A \texttt{github\_token} must reach both \texttt{update\_branch\_status} (for private
    repo branch creation via GitHub API) and \texttt{git\_clone\_or\_fetch} (for
    authenticated clone). Dropping the token causes silent 401 errors on private repos.

  \item \textbf{test\_custom\_strategies\_propagated} ---
    Custom \texttt{chunker\_strategy="ast"} and \texttt{embedding\_strategy="cohere"} must
    be forwarded to \texttt{chunk\_files} and \texttt{embed\_chunk\_batch} respectively.
    If silently replaced by defaults, the user gets wrong results with no error.

  \item \textbf{test\_latest\_commit\_in\_final\_status} ---
    The final \texttt{update\_branch\_status(status="indexed")} must include
    \texttt{latest\_commit} from the git output, while the initial
    \texttt{status="indexing"} call must have \texttt{latest\_commit=None}.
    Swapping these would record a stale or null commit SHA.
\end{enumerate}

\subsection{Cleanup Correctness and Return Value Tests}

\begin{enumerate}[resume]
  \item \textbf{test\_cleanup\_receives\_correct\_batch\_id} ---
    On failure after chunking, \texttt{cleanup\_staging} must receive the exact
    \texttt{batch\_id="batch-001"} returned by \texttt{chunk\_files}. A wrong batch ID
    would leak staging rows while potentially purging unrelated data.

  \item \textbf{test\_return\_value\_format} ---
    With \texttt{full\_name="myorg/myrepo"} and \texttt{branch="feature/cool"}, the return
    string must be \texttt{"Indexed myorg/myrepo/feature/cool at abc123"}. Branch names
    with slashes must not be truncated. This serves as a regression test for string
    interpolation used in observability logging.
\end{enumerate}
