\section{Context for Our Project: Lighthouse}

Lighthouse is a code search engine exposed via the Model Context Protocol (MCP) that
improves the performance of AI coding agents by surfacing relevant context from a
codebase. A developer selects GitHub repositories to index, Lighthouse ingests and
indexes them, and the developer adds the Lighthouse MCP server to their AI coding
agent. When the agent is working on a task and needs context that falls outside its
immediate working scope, it queries Lighthouse to retrieve relevant code snippets,
interfaces, and documentation.\\

The system is composed of several services: an \textbf{ingestion service} that clones
repositories, chunks source files, generates embeddings, and stores them in Postgres
and Milvus (vector database) via Temporal (distributed, durable execution solution) workflows; a \textbf{search service} that implements retrieval
strategies (e.g.\ hybrid search combining dense vector similarity with sparse keyword
matching); an \textbf{MCP server} that exposes search as MCP tools consumable by coding
agents; and a \textbf{web service} for management and visualization (currently used for debugging).

\subsection{Current State}

We have implemented a baseline version of the full pipeline: repositories can be indexed
(with both full and incremental indexing), searched via the MCP server, and results are
returned to coding agents. However, several areas are still in active development:

\begin{itemize}
  \item \textbf{Web UI} --- The web service currently serves as a debugging interface
    for internal development. We are still discussing and formulating what the
    production UI will look like, and expect to redesign it in the coming week.
  \item \textbf{Evaluation suite} --- We are developing an eval suite to measure how
    effectively Lighthouse improves coding agent outcomes, building on the aspirational
    dataset design from A2. This will let us quantitatively compare retrieval strategies.
  \item \textbf{Search and ingestion experimentation} --- We are experimenting with
    different search strategies, chunking approaches (e.g.\ sliding window vs.\
    AST-aware chunking), and embedding models to improve retrieval quality beyond
    our current baseline.
\end{itemize}

\subsection{Tech \& Testing Stack}
Below are quick descriptions of each services (found in \texttt{services/}) tech stack:
\begin{itemize}
  \item \texttt{ingestion} --- A Python 3.11 service built with FastAPI and Temporal.
    It uses GitPython for repository cloning, our shared workspace packages
    (\texttt{shared}, \texttt{db}, \texttt{vectordb}, and \texttt{embedding}) for
    schemas and storage, and implements the indexing pipeline including chunking,
    embedding generation, and workflow orchestration.
  \item \texttt{search} --- A Python 3.11 FastAPI service that implements retrieval
    logic. It uses the same shared workspace packages as the ingestion service and
    contains our search strategies, including hybrid search over Postgres and Milvus.
  \item \texttt{mcp\_server} --- A Python 3.11 service built with FastAPI and
    FastMCP. It exposes Lighthouse functionality as MCP and HTTP endpoints for coding
    agents, and also uses \texttt{httpx}, \texttt{cryptography}, \texttt{asyncpg},
    and \texttt{boto3} for integration with authentication, persistence, and external
    services.
  \item \texttt{web} --- A TypeScript frontend built with React 19 and Vite. It uses
    React Router for navigation, SWR for client-side data fetching, and Tailwind CSS
    for styling; at the moment it primarily serves as an internal debugging and
    management UI.
\end{itemize}

For testing, our testing framework is \texttt{pytest}, with tests organized
into \texttt{unit}, \texttt{integration}, and \texttt{e2e} markers. We use
\texttt{pytest-asyncio} for async service and API tests, and \texttt{pytest-cov} to
measure line coverage across the Python services and shared packages. For
infrastructure-dependent tests, we use \texttt{testcontainers} to provision isolated
Postgres and Milvus instances during test runs instead of depending on shared
developer machines. Since Temporal is a core part of the ingestion pipeline, we also
use Temporal Python SDK testing utilities such as
\texttt{temporalio.testing.WorkflowEnvironment} and
\texttt{ActivityEnvironment} to test workflow orchestration and activities in a
deterministic local environment.

\section{Profiling Execution time}
% Profile 5 important functions in your codebase using https://docs.python.org/3/library/profile.html.
% Analyze your functions and find ways to improve them.

We performed profiling benchmarks of some significant hot paths in our function, focusing mostly on our intensive ingestion and search services. The raw benchmark results of the pre-improvement baselines can be seen in Appendix~\ref{app:prof_baseline} and the improved performance data can be seen in Appendix~\ref{app:prof_improved}. \\

\textbf{1. SlidingWindowChunker.chunk\_file}

In the baseline profile (\texttt{profiling\_results.tmp}), \texttt{chunk\_file} accounted for a cumulative \texttt{0.010s} across 3 calls. The function itself was not dominated by loop control logic; instead, the profile showed repeated per-chunk work from hashing and string processing. In particular, \texttt{compute\_chunk\_hash} contributed \texttt{0.003s} cumulative, with \texttt{\_hashlib.openssl\_sha256} at \texttt{0.002s}. This indicated that for medium-to-large chunk counts, hash choice materially affected end-to-end chunking latency. \\

The optimization focused on replacing SHA-256 with xxHash64 in \texttt{compute\_chunk\_hash}, while keeping the chunking algorithm and output semantics unchanged. This is appropriate because the hash is used for chunk identity/dedup behavior rather than cryptographic verification, so we don't need the full security guarantees of something like SHA-256. xxHash64 significantly reduces CPU cost per hash invocation while still providing practical collision resistance for this operational context. xxHash also allows for a larger 128-bit option which would reduce the chance of hash collisions significantly, though only extremely large codebases would even run the risk of collision in a 64-bit space. \\

In the post-change profile (\texttt{profiling\_results\_after\_improvements.tmp}), \texttt{chunk\_file} dropped to \texttt{0.006s} cumulative across 3 calls (about 40\% faster). Hashing is no longer a visible dominant cost: \texttt{compute\_chunk\_hash} and \texttt{xxhash.\_xxhash.xxh64\_hexdigest} both register effectively as near-zero at this scale. The remaining visible work is mostly \texttt{splitlines}, \texttt{join}, and baseline iteration overhead. \\

\textbf{2. GitOperations.list\_files}

Before optimization, \texttt{list\_files} took \texttt{0.216s} cumulative across 2 calls. The profile showed expensive traversal behavior centered on \texttt{pathlib.rglob} and related selector machinery: \texttt{rglob} at \texttt{0.081s}, selector internals at \texttt{0.078s}, and heavy \texttt{stat}/\texttt{is\_file} traffic (\texttt{stat} at \texttt{0.077s}, \texttt{is\_file} at \texttt{0.059s}). The key issue was traversal and path-object overhead rather than filtering logic alone. \\

The implementation was changed to use \texttt{os.walk} traversal with inline filtering. This avoids the \texttt{pathlib} selector/rglob overhead, reduces object churn, and keeps filtering close to candidate discovery. The behavior contract was retained: same extension checks, same skip patterns, same size threshold, and exclusion of \texttt{.git}-internal content. \\

After optimization, \texttt{list\_files} improved to \texttt{0.158s} cumulative across 2 calls (about 27\% faster). The hotspot shape also shifted as expected: \texttt{rglob} and selector frames disappeared, replaced by \texttt{os.\_walk} and direct path/stat operations. This confirms that the improvement came from cheaper traversal mechanics, not from reduced output scope (\texttt{listed\_files} remained \texttt{4860} in both runs). \\

\textbf{3. ChunkService.move\_to\_final}

In the baseline, \texttt{move\_to\_final} consumed \texttt{1.822s} cumulative for the 8k-chunk profile case. Most of that time sat in ORM SQL generation and execution pathways: SQL construction (\texttt{1.036s}), internal SQL building (\texttt{1.035s}), and insert generation (\texttt{1.027s}). Additional cost came from staging row materialization and conversion (\texttt{process\_row}, \texttt{python\_value}, date/time adaptation paths). This profile clearly identified the expensive portions as ORM shaping plus per-row conversion overhead. \\

The maintainable optimization path preserved Peewee inserts (raw SQL insert path was intentionally reverted) and instead reduced per-row overhead where safe:
\begin{itemize}
\item read only required staging columns,
\item fetch staging rows as tuples instead of full model instances,
\item centralize embedding normalization/decoding in a lightweight helper.
\end{itemize}
These changes keep transactional behavior and output semantics intact while lowering model-instantiation and field-conversion pressure. \\

After these adjustments, \texttt{move\_to\_final} dropped to \texttt{1.260s} cumulative (about 31\% faster). ORM SQL generation remains the dominant cost center, but the total envelope is significantly reduced. The profile confirms reduced pressure from row-conversion-heavy portions compared to baseline, while preserving current maintainability constraints. \\

\textbf{4. HybridSearchStrategy.search}

Baseline search profiling showed \texttt{search} at \texttt{0.062s} cumulative for 2 calls, with the main internal hotspot concentrated in publish filtering:

\texttt{\_filter\_vector\_results} at \texttt{0.042s} and \texttt{\_get\_active\_publish\_map} at \texttt{0.042s}.  
This pointed to query-shape inefficiency (large OR predicate construction/execution) rather than fusion or snippet rendering. Supporting ORM SQL frames reinforced that diagnosis.

The optimization replaced OR-heavy publish-map lookup with a grouped and batched strategy:
\begin{itemize}
\item deduplicate \((repository, branch, file\_path)\) keys before querying,
\item group lookups by \((repository, branch)\),
\item issue batched \texttt{IN (...)} queries for file paths.
\end{itemize}
Additional low-risk trims were included:
\begin{itemize}
\item cap vector overfetch to prevent unnecessary widening in lookup workloads,
\item build score map only for top-\(k\) fused entries used for final snippet scoring.
\end{itemize}

After optimization, overall \texttt{search} time dropped to \texttt{0.023s} cumulative for 2 calls (about 63\% improvement). Internal hotspot reductions are substantial: \texttt{\_get\_active\_publish\_map} decreased from \(\sim\)\texttt{0.042s} to \(\sim\)\texttt{0.005s}, and \texttt{\_filter\_vector\_results} decreased from \(\sim\)\texttt{0.042s} to \(\sim\)\texttt{0.006s}. Fusion remained inexpensive, confirming that the dominant gain came from improved DB query shape and key-set handling. \\

\textbf{5. ChunkService.publish\_incremental\_batch}

Baseline profiling showed \texttt{publish\_incremental\_batch} at \texttt{2.530s} cumulative for 3 calls in the 8k-chunk / 200-file workload. The dominant costs were concentrated in ORM-heavy paths and per-file upsert logic: SQL generation (\texttt{1.518s}), insert generation (\texttt{0.954s}), and repeated per-file \texttt{get\_or\_create} activity (\texttt{0.580s} cumulative for \texttt{600} calls across repeats). Additional overhead came from row materialization/conversion (\texttt{process\_row}, \texttt{python\_value}, date parsing/formatting paths), indicating that object hydration and query construction were significant contributors. \\

The implementation was optimized without changing external behavior. First, staging reads were moved to a column-limited \texttt{select(...).tuples()} shape so the method operates on lightweight tuple rows instead of hydrated model instances. Second, file tracking was reduced from a per-file list map to a set of staged file paths, since only membership checks are required for publish decisions. Third, embedding decoding was normalized through the shared \texttt{\_decode\_embedding} path to remove duplicate branch/convert logic in this function. Fourth, chunk inserts remained batched via Peewee but are now built from tuple rows, reducing repeated attribute access overhead. Fifth, the per-file \texttt{get\_or\_create + save} loop was replaced with batched \texttt{insert\_many(...).on\_conflict(update=...)} upserts on \texttt{indexed\_files}, updating \texttt{active\_publish\_id} and \texttt{updated\_at} in bulk. \\

After these changes, the same benchmark improved from \texttt{2.530s} to \texttt{1.447s} cumulative, a reduction of about \textbf{43\%}. The hotspot profile still shows ORM SQL generation as the leading cost center, but the expensive per-file upsert pattern and model-materialization overhead were substantially reduced while preserving publish semantics and cleanup behavior.

\section{Test Coverage Depth}
% Choose your most complex module in your codebase. Create at least 10 unit tests for this module that

Our most complex module is the \texttt{IndexBranchWorkflow} in the ingestion service

(\bluehref{https://github.com/UofT-CSC490-W2026/Lighthouse/blob/a5/services/ingestion/src/ingestion/temporal/workflows/index\_branch.py}{services/ingestion/src/ingestion/temporal/workflows/index\_branch.py}).
This Temporal workflow orchestrates 7 distinct activities through a multi-step pipeline:
marking a branch as indexing, cloning the repository, chunking files into a staging table,
deleting old chunks, embedding chunks in parallel batches, storing results to the final
tables and vector database, and updating the branch status. It includes conditional
early-exit logic (when no chunks are produced), parallel fan-out for embedding batches
(using \texttt{asyncio.gather}), and a two-phase error handler that marks the branch as
failed and conditionally cleans up staging data only when a \texttt{batch\_id} has been assigned. \\

All 12 tests are located in
\bluehref{https://github.com/UofT-CSC490-W2026/Lighthouse/blob/a5/services/ingestion/tests/unit/test\_index\_branch\_workflow.py}{services/ingestion/tests/unit/test\_index\_branch\_workflow.py} and use Temporal's
\texttt{WorkflowEnvironment} with mocked activities. This isolates the workflow's
orchestration logic from external dependencies (Postgres, Milvus, git, OpenAI), allowing
us to test decision-making, parameter threading, and failure handling.
Each test and the reasoning behind why we chose it is commented in the code.

\subsection{Boundary Tests (Positive)}

These tests target the embed batching loop, which uses
\texttt{range(0, chunk\_count, EMBED\_BATCH\_SIZE)} where \texttt{EMBED\_BATCH\_SIZE = 512}.
Off-by-one errors in this loop would cause chunks to be silently skipped or duplicated.

\begin{enumerate}
  \item \textbf{test\_single\_chunk\_produces\_one\_embed\_batch} -
    \texttt{chunk\_count=1} produces exactly 1 embed call at offset 0.
    Tests the lower boundary of the batching loop.

  \item \textbf{test\_exactly\_512\_chunks\_one\_batch} -
    \texttt{chunk\_count=512} (exactly \texttt{EMBED\_BATCH\_SIZE}) produces exactly 1 batch.
    This is the upper boundary for a single batch; a fencepost error would produce 0 or 2 batches.

  \item \textbf{test\_513\_chunks\_two\_batches} ---
    \texttt{chunk\_count=513} is the smallest value that requires 2 batches.
    Verifies offsets are \texttt{[0, 512]}.

  \item \textbf{test\_large\_chunk\_count\_batch\_offsets} -
    \texttt{chunk\_count=2049} produces 5 batches with offsets
    \texttt{[0, 512, 1024, 1536, 2048]}.
    Validates batch arithmetic at scale.
\end{enumerate}

\subsection{Failure Mode Tests (Negative)}

These tests verify that the workflow correctly handles exceptions at different stages.
The key invariant: \texttt{cleanup\_staging} is called if and only if \texttt{batch\_id}
was set (i.e., \texttt{chunk\_files} succeeded).

\begin{enumerate}[resume]
  \item \textbf{test\_delete\_failure\_triggers\_cleanup} -
    \texttt{delete\_existing\_chunks} fails \emph{after} \texttt{batch\_id} is assigned.
    Verifies both \texttt{status="failed"} and \texttt{cleanup\_staging} are called.
    This failure point was not covered by existing e2e tests.

  \item \textbf{test\_store\_failure\_triggers\_cleanup} -
    \texttt{store\_chunks} fails after embedding succeeds.
    Embedded staging rows must be cleaned up to avoid dangling data.

  \item \textbf{test\_chunk\_files\_failure\_no\_cleanup} -
    \texttt{chunk\_files} raises \emph{before} \texttt{batch\_id} is assigned.
    Verifies \texttt{cleanup\_staging} is \textbf{not} called (there is nothing to clean),
    validating the \texttt{if batch\_id is not None} guard in the exception handler.
\end{enumerate}

\subsection{Parameter Propagation Tests (Positive)}

These tests verify that input parameters are correctly threaded through to the right activities.
Silent parameter drops would cause production failures with no error signal.

\begin{enumerate}[resume]
  \item \textbf{test\_github\_token\_propagated} -
    A \texttt{github\_token} must reach both \texttt{update\_branch\_status} (for private
    repo branch creation via GitHub API) and \texttt{git\_clone\_or\_fetch} (for
    authenticated clone). Dropping the token causes silent 401 errors on private repos.

  \item \textbf{test\_custom\_strategies\_propagated} -
    Custom \texttt{chunker\_strategy="ast"} and\\ \texttt{embedding\_strategy="cohere"} must
    be forwarded to \texttt{chunk\_files} and \texttt{embed\_chunk\_batch} respectively.
    If silently replaced by defaults, the user gets wrong results with no error.

  \item \textbf{test\_latest\_commit\_in\_final\_status} -
    The final \texttt{update\_branch\_status(status="indexed")} must include
    \texttt{latest\_commit} from the git output, while the initial
    \texttt{status="indexing"} call must have \texttt{latest\_commit=None}.
    Swapping these would record a stale or null commit SHA.
\end{enumerate}

\subsection{Cleanup Correctness and Return Value Tests}

\begin{enumerate}[resume]
  \item \textbf{test\_cleanup\_receives\_correct\_batch\_id} -
    On failure after chunking, \texttt{cleanup\_staging} must receive the exact
    \texttt{batch\_id="batch-001"} returned by \texttt{chunk\_files}. A wrong batch ID
    would leak staging rows while potentially purging unrelated data.

  \item \textbf{test\_return\_value\_format} -
    With \texttt{full\_name="myorg/myrepo"} and \texttt{branch="feature/cool"}, the return
    string must be \texttt{"Indexed myorg/myrepo/feature/cool at abc123"}. Branch names
    with slashes must not be truncated. This serves as a regression test for string
    interpolation used in observability logging.
\end{enumerate}

    \item Here is a \bluehref{https://docs.google.com/presentation/d/1oTm824FbHy6FvsnDb1Oj1ypalQ6g7qS3t5RsoxHJR8k/edit?usp=sharing}{link} to the slides shown in the video.

\subsection{Summary}

\textbf{Context:} The \bluehref{https://github.com/UofT-CSC490-W2026/Lighthouse/blob/a5/services/ingestion/src/ingestion/temporal/workflows/incremental.py}{\texttt{IncrementalIndexWorkflow}} is a Temporal workflow
triggered by GitHub webhooks that re-indexes changed repository files into the search
pipeline. On each invocation it clones the updated branch, chunks modified files,
generates embeddings, and writes results into Postgres and Milvus so that search
reflects the latest code. \\

\textbf{Bug 1: Temporary Gap in Searchable Data.} The workflow deleted existing
search chunks for changed files before their replacements were ready, creating a
window during which a recently modified file was invisible to search. The fix
introduced a publish-and-switch model: new chunks are staged under a
\texttt{publish\_id} and only promoted to active once fully written, so old data
remains searchable until the new version is ready. This taught us that correctness
is not only about eventually producing the right data. It is
also about what is visible at every intermediate state. It also showed us that background tasks can also have big ripple effects.
\\

\textbf{Bug 2: Catastrophic Deletion on Failure.} If any step failed after
deletion (during chunking, embedding, or storage) the workflow would terminate
without restoring the removed chunks, leaving those files absent from search until a
future successful re-index. The publish-and-switch architecture resolves this as
well: because deletion no longer precedes the publish, a failure at any point leaves
the active search data exactly as it was before the workflow began. This highlighted
that orchestration order is crucial and retry logic introduces complexity.
